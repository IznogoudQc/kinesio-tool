# 2026-09-28 — Marie est prévenue quand une cliente écrit dans Effet

Livré en v0.9.237 et v0.9.238 (repli `.env` en dev).

## Demande

Les clientes écrivent depuis Effet, Marie ne le savait qu'en ouvrant la console.
Il fallait une notification sur son bureau, sans rien ouvrir.

## Ce qui a été fait

Une veille dans le processus principal : `GET /coach/fils` toutes les 150 s, et
une notification Windows quand une cliente a écrit. Détails et justifications
dans [[docs/decisions/0045-veille-messages-effet]].

| Fichier | Rôle |
|---------|------|
| `src/lib/effet-notifications.ts` | Les décisions — qui notifier, quel texte, quoi mémoriser. Sans Electron, donc testable. |
| `src/lib/effet-notifications.test.ts` | 15 tests, `node --test` |
| `electron/lib/effet-api.ts` | L'appel HTTP et les trois réponses du contrat |
| `electron/lib/effet-notifications-service.ts` | Minuterie, fichier d'état, notification, journal |
| `electron/ipc/effet-notifications.ts` | Ce que l'interface peut demander |
| `src/pages/settings/EffetNotificationsCard.tsx` | L'interrupteur et l'heure du dernier contrôle |

## La contrainte qui a tout guidé

**Le texte d'un message ne sort jamais.** Une cliente : « Julie t'a écrit ».
Plusieurs : « 3 nouveaux messages ». Marie reçoit ses clientes dans la même
pièce que son écran.

Le champ `apercu` arrive bien dans la réponse de l'API, mais il s'arrête à
`filsANotifier` : ni notification, ni journal, ni fichier d'état. C'est la règle
la plus facile à casser par accident — un jour où l'on voudra « rendre service »
en montrant le début du message. Le dernier test du fichier la verrouille : il
sérialise les trois sorties et vérifie qu'aucune ne contient le texte.

## Deux choses à savoir

**L'heure de dernière vérification n'avance que sur un contrôle abouti.** Sinon
l'interface mentirait sur la fraîcheur de ce qu'elle montre, et Marie ne pourrait
pas distinguer « personne ne m'a écrit » de « ça ne marche plus ».

**L'interrupteur coupe les notifications, pas le sondage.** L'heure continue
d'avancer pendant une séance, ce qui permet de vérifier que la veille tourne
toujours.

## Reste à trancher

~~La clé est lue dans le `.env`~~ — tranché le jour même : le `.env` n'était de
toute façon jamais chargé dans `process.env`, et il n'existe pas chez Marie. La
clé se saisit dans Paramètres et est chiffrée par `safeStorage` (voir ADR 0045).

Au premier lancement, le fichier d'état est vide : la première vérification
mémorise tous les fils en cours **sans** les annoncer. Conséquence assumée — un
message reçu juste avant l'installation ne produira pas de notification.

## Repli `.env` pour le poste de développement

Paramètres reste la source de la clé ; en dev seulement (`!app.isPackaged`),
si rien n'y est enregistré, la clé est lue dans `EFFET_API_KEY` — variable
d'environnement, sinon `.env` à la racine du dépôt, lu à l'exécution (le
`.env` a été renommé en conséquence : `EFFET_CLE` → `EFFET_API_KEY`). La clé
n'entre donc jamais dans le build, et une application installée ne lit jamais
de `.env` : l'ADR 0045, qui écarte le `.env` comme source en production, tient
toujours.

La carte dit d'où vient la clé sans jamais la montrer : « Une clé est
enregistrée. » ou « Clé lue dans le .env (poste de développement). », avec un
bouton « Remplacer ».

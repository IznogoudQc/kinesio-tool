## v0.9.29 — Étiquette du dernier point rognée sur les graphes de tendance

**Symptôme** (capture Marie / Nicholas) : la valeur du dernier point des courbes était coupée — « % » rogné
à droite sur le % de gras, « 4 / 4 » illisible en haut à droite sur le score de composition.

**Diagnostic** : l'étiquette (`textAnchor="middle"`) est centrée sur le dernier point, qui n'est qu'à
`R = 14` px du bord droit → la moitié du texte (~40 px) sort du `viewBox`. Et sur `ScoreTrend` (échelle
0-4 figée, sans marge haute), un score de 4 place le point à `py(4) = 12` → étiquette à `y = 3`, tronquée
par le haut.

**Correctif** (identique dans `ScoreTrend.tsx`, `BodyFatTrend.tsx`, `Vo2maxTrend.tsx`) :
- `lastLabelX = Math.min(lastX, W - 24)` → plus de débordement à droite.
- `lastLabelY = lastLabelAbove ? lastY - 9 : lastY + 20` (bascule sous le point si `lastY - 20 < 0`).

**Vérif** : tsc web + node propres, `eslint` propre, `node --test` 324 pass, `npm run build` OK.

**Reste à voir** : les rapports PDF (`ReportPage.tsx`) / HTML (`EditorialReport.tsx`) ont leurs propres
rendus de graphiques — vérifier si le même motif d'étiquette y existe (même bug potentiel).

## v0.9.30 — Indice de santé du dos : parité exacte (enquête + correctif)

**Demande** : « on va travailler sur l'indice du dos, est-ce que tu as maintenant toutes les informations
pour avoir la même valeur que l'ancien logiciel ? » Marie a fourni les Fig. 7-24 à 7-27 du guide CPHV.
Bilan de référence : **3,6** (25 juin 2026).

**Méthode** : rétro-calcul depuis les rapports Word réels du logiciel d'origine (`~/Downloads`, lus via
`antiword` puis LibreOffice → `.docx` → mammoth, la conversion donnant des tableaux bien plus lisibles).
6 bilans exploités (2011, 2025-09, 2025-12, 2026-01, 2026-02, 2026-06).

**Deux découvertes** :
1. Les bilans de déc. 2025 / janv. / févr. 2026 ne contiennent **aucun test musculo** — seulement le tour
   de taille — et affichent quand même un indice de 2,0. Ça **isole la cote du tour de taille** et permet
   de la lire directement.
2. Le score est **décimal** (3,6 / 2,6 / 1,7) → l'ancien logiciel n'applique **pas** le nomogramme
   (Fig. 7-25), qui produit des entiers. Le nomogramme n'est que l'arrondi du même rapport.

**Formule confirmée** : `Σ(cote × poids) ÷ Σ(poids)`, poids Fig. 7-24, sans arrondi, la cote du tour de
taille venant des tables de **composition** (Fig. 7-4/7-5, dépend de l'IMC) — pas d'une table « tour de
taille » autonome. Vérifié **5/5** pour le dos et **3/3** pour le musculo (voir ADR 0028 pour le tableau).

**Correctifs** : `cpaflaCombine` ne rounde plus (arrondi déplacé dans `cpaflaNomogramme`) ; nouveau
`cpaflaWaistPoints` ; `bilan-computed` applique la méthode dès que le sexe est connu, quelle que soit la
norme ; `DEFAULT_NORMS` (+ son doublon IPC) passe à `cpafla`.

**Vérif** : `node --test` 328 pass (dont `cpafla-parite.test.ts`), tsc web + node propres, `eslint` propre.
Bout en bout via `computeBilan` sur le bilan du 25 juin 2026 → dos **3,6**, musculo **3,7**,
composition **4,0** : identiques au rapport.

**Reste ouvert** : le score global (« Santé et Condition Physique Globale ») ne matche pas encore —
aucune combinaison testée ne reproduit à la fois 2,2 (sept. 2025) et 4,0 (juin 2026).

## v0.9.32 — Import .doc : scores recalculés, pas recopiés

**Question de Nicholas** : « pour être sûr, l'indice du dos et l'aptitude musculosquelettique sont bien
calculés quand je fais un import de doc ? C'est pas seulement une copie du vieux bilan ? »

**Audit** — la réponse était *oui pour le dashboard, non pour le formulaire* :

| Où | Source |
|---|---|
| Dashboard, rapports PDF/HTML | **recalculé** (`computeBilan` ne lit jamais `indice_sante_dos`) ✓ |
| Formulaire de bilan → « Indices (calculés) » | **la copie** du vieux rapport ✗ |

Le parser extrait bien `indice_sante_dos` / `score_musculo_global` / `score_composition` / `score_global`
(`bilan-parser.ts` l.151-154), `ImportBilanModal.handleSave` enregistrait les données **telles quelles**, et
`mergeComputedIntoBilan` n'écrasait pas ces champs. Sur les bilans récents les deux coïncident (parité
v0.9.30), mais pas sur **2011** : le vieux rapport y inclut le questionnaire d'activité physique que l'app
n'utilise pas → 1,7 (copié) vs ~2,0 (calculé).

**Correctifs** :
1. `mergeComputedIntoBilan` écrit les 4 scores composites depuis `computed` (arrondis à la décimale).
2. `ImportBilanModal` fait passer le bilan courant **et** chaque historique par `deriveBilanFields`, avec
   `computeAge(birthdate, date_du_bilan)` — l'âge à la date du bilan, pas aujourd'hui (un historique peut
   avoir 15 ans ; utiliser l'âge courant fausserait toutes les cotes).
3. Reliquat de v0.9.31 : `norms: 'acsm'` codé en dur dans `deriveBilanFields` (`BilanForm.tsx`),
   `NutritionTab`, et les défauts de props de `BilanForm` / `AerobicSection` / `StatCardXL`. Comme la
   **composition** branche encore sur `profile.norms === 'cpafla'`, ces chemins la calculaient avec
   l'ancienne moyenne ACSM. Tous passés à `DEFAULT_NORMS`.

**Test de non-régression** (`bilan-computed.test.ts`) : on injecte `indice_sante_dos: 99` etc. dans les
mesures réelles du 25 juin 2026 et on vérifie que le merge rend bien 3,6 / 3,7 / 4.

**Vérif** : tsc web + node propres, `eslint` propre, `node --test` **329 pass**, `npm run build` OK.

## v0.9.33 — Une seule feuille de saisie : la puissance des jambes aussi recalculée

**Question de Nicholas** : « je veux être sûr, quand on importe un vieux bilan, on copie seulement les
données nécessaires pour calculer les valeurs. Ça devrait être la même chose que la saisie manuelle. Lors
d'un import, est-ce qu'on pourrait utiliser la même feuille d'entrée de données ? »

**Constat 1 — c'est déjà le cas pour le formulaire** : `ImportBilanModal` rend le **même** `BilanForm` que
la saisie manuelle (seul `variant="light"` change la palette). Rien à faire.

**Constat 2 — il restait UNE valeur dérivée recopiée** : la puissance des jambes. Le parser posait
`puissance_calculated_auto = false` (`bilan-parser.ts` l.165) et `computeBilan` avait une branche explicite
« préserver les valeurs importées ».

**Décision** : la puissance est un champ `type: 'computed'` du formulaire — Marie ne peut **pas** la saisir.
La seule source d'une valeur non-Sayers était donc l'import. Branche de préservation retirée : Sayers
s'applique dès que saut + poids sont connus, et la valeur importée ne sert plus que de repli si le calcul
est impossible. Idem dans `mergeComputedIntoBilan` (garde simplifiée).

**Preuve que Sayers est bien la formule d'origine** (`60.7 × saut + 45.3 × poids − 2055`) :

| Bilan | Saut | Poids | Sayers | Rapport |
|---|---|---|---|---|
| 2025-09 | 48 | 99,8 | **5380** | 5380 ✓ |
| 2011-08 | 42 | 99,2 | **4988** | 4988 ✓ |
| 2026-06 | 48 | 91,8 | **5017** | 4725 ✗ |

Le vieux rapport déclare lui-même utiliser Sayers ; pour juin 2026 sa valeur est incohérente avec le saut
et le poids qu'il imprime (il faudrait un saut de 43,2 cm ou un poids de 85,4 kg). C'est donc le rapport
d'origine qui est en défaut, pas notre calcul. **Effet visible** : ce bilan passera de 4725 à 5017 W.

**Tests** : puissance importée absurde (1234) écrasée par 5380 ; puissance conservée si le saut manque.

**Vérif** : tsc propre, `node --test` **331 pass**, `npm run build` OK.

partagés au lieu d'être dupliqués. Seule spécificité conservée à l'import : la liste des bilans plus
